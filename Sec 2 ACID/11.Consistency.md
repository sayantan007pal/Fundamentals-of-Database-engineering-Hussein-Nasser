## 1. The one picture

Hussein's table (also in [read.pdf](read.pdf)):

```text
id   1    2    3    4    5    6
val  aa   bb   bb   bb   aa   aa
     three aa, three bb
```

T1: change every `aa` → `bb`.  
T2: change every `bb` → `aa`.

If they ran **one after the other**, the only legal endings are **all aa** or **all bb**. A reader who photographs the table **while both are committing at Read Committed** can get a mix. Every cell is valid ink. The **photo** is a lie about the whole sign.

```text
data consistency (ACID C)     every letter is on the menu (CHECK passed)
read consistency              the photo is one finished sign, not two half-paints
replica consistency           the branch kiosk may still show yesterday's finished sign
```

Those are three jobs. This lecture is the first two. The kiosk is lecture 16.

## 2. Simulation — watch it happen

### Simulation 1 — letter-swap report (read consistency)

Start:

```text
committed table     aa bb bb bb aa aa
```

**Pause and predict:** T1 commits its three `aa→bb`. Before T2 finishes, a reader at Read Committed runs `SELECT *`. Can that result be a state that never existed if T1 and T2 had run serially?

**Reveal — yes.**

```text
Tick R1 — T1 COMMIT: the three aa became bb
committed truth     bb bb bb bb bb bb     (all bb, if T1 ran alone)

Tick R2 — T2 has updated some of its bb→aa and COMMITs in pieces
          (or a second statement in the reader takes a new snapshot)

Reader at READ COMMITTED, two statements (or a scan that sees two commit points)
          e.g.  bb  aa  bb  bb  aa  bb
                ────────────────────────
                every cell is committed
                CHECK (val IN ('a','b')) still true
                this mix is not all-aa and not all-bb
                no serial schedule produces it
```

Atomicity did not fail (each writer was all-or-nothing). CHECK did not fail. **The read was stitched from two commit points.** That is read consistency, implemented by isolation (lecture 10): freeze one snapshot for the whole report (`REPEATABLE READ` / Snapshot / Serializable).

Serial endings if they do not overlap in time:

```text
T1 then T2 → all aa
T2 then T1 → all bb
```

The swapped mix (lecture 15) is what happens when **both writers commit** under Repeatable Read. Simulation 1 is the **reader** seeing a mash-up; lecture 15 is the **writers** leaving a mash-up.

### Simulation 2 — two $80 withdrawals from $100 (data consistency)

Alice has $100. Rule: balance never negative. Schema has `CHECK (balance >= 0)`.

```text
START
committed truth     Alice 100
CHECK               100 >= 0  ok
```

T1 and T2 both run at Read Committed. Each **reads** 100 in the application, then writes `balance = 20`.

**Pause and predict:** Does CHECK fire? Final Alice = ?

**Reveal:**

```text
Tick W1 — T1 SELECT → 100. T2 SELECT → 100.
committed truth     Alice 100

Tick W2 — T1 UPDATE SET balance = 20; COMMIT;
committed truth     Alice 20
CHECK               20 >= 0  ok

Tick W3 — T2 UPDATE SET balance = 20; COMMIT;
committed truth     Alice 20
CHECK               20 >= 0  ok     ← the engine checked the ROW T2 wrote
total withdrawn     160 from 100    ← the invariant is dead
```

CHECK is **row-local, at write time**. It cannot see T2's stale arithmetic. Two legal statements produced an illegal **business** state.

Fixes (all three engines, below): atomic `UPDATE ... WHERE balance >= 80`, `SELECT FOR UPDATE`, or Serializable. Isolation is the tool; consistency is the **outcome**.

## 3. Why the engine does that

Only **after** those two pictures, name the three C's:

| Meaning | Question | Who enforces it |
|---------|----------|-----------------|
| **Data (ACID C)** | After COMMIT, do declared rules and your invariants still hold? | Engine: PK, FK, CHECK, NOT NULL. App: "total money," "at least one doctor." |
| **Read** | Did this query/transaction see **one** commit point? | Isolation / MVCC snapshot / `readConcern: snapshot` |
| **Replica** | Did **another node** see the write yet? | Replication. Lecture 16. Not CHECK. |

```text
Atomicity     forbids a half-applied transaction
Isolation     controls whose photocopy you hold
Consistency   is the result: valid state → valid state, and a coherent read
```

### Who owns which rule?

| Rule | Example | Enforced by |
|------|---------|-------------|
| NOT NULL / UNIQUE / PK | every account has an id | DB |
| FOREIGN KEY | sale references a real product | SQL engines. **Not** MongoDB (app or embed). |
| CHECK / `$jsonSchema` | `balance >= 0`, `price > 0` | DB, **per document/row**, at write |
| Cross-row invariant | sum of credits = sum of debits; two withdrawals | App + atomic SQL / locks / Serializable |
| Process invariant | ship only after payment | App (workflow), optionally triggers |

PostgreSQL: `CHECK` is **immediate** and must not query other rows. `SET CONSTRAINTS DEFERRED` applies to deferrable **UNIQUE / PK / FK / EXCLUDE**, not to CHECK or NOT NULL.

InnoDB: MySQL 8.0.16+ enforces CHECK unless `NOT ENFORCED` (parsed, ignored — interview trap). FKs work only on **InnoDB**, not MyISAM.

MongoDB: `$jsonSchema` + unique indexes. **No declarative FK.** `$lookup` is a join, not a constraint.

## 4. Same idea in three engines

### Setup — data rules

**PostgreSQL / portable SQL:**

```sql
CREATE TABLE accounts (
  id      INT PRIMARY KEY,
  name    TEXT NOT NULL,
  balance NUMERIC(10,2) NOT NULL CHECK (balance >= 0)
);
CREATE TABLE transfers (
  id           INT PRIMARY KEY,          -- SERIAL in PG; AUTO_INCREMENT in MySQL
  from_account INT NOT NULL REFERENCES accounts(id),
  to_account   INT NOT NULL REFERENCES accounts(id),
  amount       NUMERIC(10,2) NOT NULL CHECK (amount > 0)
);
INSERT INTO accounts VALUES (1, 'Alice', 100.00), (2, 'Bob', 50.00);
```

### PostgreSQL — Simulation 2 fix + deferred FK + letter reader

```sql
-- CHECK fires (row-local)
UPDATE accounts SET balance = balance - 250 WHERE id = 1;
-- ERROR: new row violates check constraint

-- CHECK does NOT save two concurrent app-computed writes.
-- Fix 1: atomic condition
UPDATE accounts SET balance = balance - 80
 WHERE id = 1 AND balance >= 80;
-- 0 rows → insufficient funds

-- Fix 2: lock then decide
BEGIN;
SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;
UPDATE accounts SET balance = balance - 80 WHERE id = 1;
COMMIT;

-- Fix 3: Serializable (retry on 40001)
BEGIN ISOLATION LEVEL SERIALIZABLE;
-- read + write
COMMIT;

-- Deferred FK: check at COMMIT, not per statement
CREATE TABLE orders (
  id INT PRIMARY KEY,
  customer_id INT NOT NULL
);
CREATE TABLE order_lines (
  order_id INT NOT NULL,
  product_no INT NOT NULL,
  PRIMARY KEY (order_id, product_no),
  FOREIGN KEY (order_id) REFERENCES orders(id) DEFERRABLE INITIALLY DEFERRED
);
BEGIN;
SET CONSTRAINTS ALL DEFERRED;
INSERT INTO order_lines VALUES (100, 42);
INSERT INTO orders VALUES (100, 1);
COMMIT;
```

Letter-swap **reader** (Simulation 1):

```sql
-- PostgreSQL / InnoDB letters table
CREATE TABLE letters (
  id INT PRIMARY KEY,
  val CHAR(1) NOT NULL CHECK (val IN ('a', 'b'))
);
INSERT INTO letters VALUES
  (1,'a'), (2,'b'), (3,'b'), (4,'b'), (5,'a'), (6,'a');

-- Reader at RC can see a mix. Freeze it:
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT id, val FROM letters ORDER BY id;  -- one photocopy
-- T1/T2 commit; second SELECT is identical
COMMIT;

-- Writers that must end all-a or all-b: SERIALIZABLE (lecture 15)
BEGIN ISOLATION LEVEL SERIALIZABLE;
UPDATE letters SET val = 'b' WHERE val = 'a';
COMMIT;  -- partner may get 40001
```

### Generic SQL / InnoDB

```sql
-- MySQL 8.0.16+ CHECK is real unless NOT ENFORCED
CREATE TABLE t1 (
  i1 INT CHECK (i1 <> 0),
  i2 INT,
  CHECK (i2 > i1),
  CHECK (i2 <> 0) NOT ENFORCED   -- documentation only
);

START TRANSACTION;
UPDATE accounts SET balance = balance - 80 WHERE id = 1 AND balance >= 80;
UPDATE accounts SET balance = balance + 80 WHERE id = 2;
COMMIT;

-- Letter reader: InnoDB default RR already freezes plain SELECT
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
START TRANSACTION;
SELECT * FROM letters ORDER BY id;  -- snapshot A
-- other session commits
SELECT * FROM letters ORDER BY id;  -- snapshot B, may differ  (Sim 1)
COMMIT;
```

FK: `ENGINE=InnoDB`. MyISAM ignores FOREIGN KEY — interview trap.

### MongoDB — schema validation, no FK, snapshot for the report

```javascript
// Data-C: shape of one document
db.createCollection("accounts", {
  validator: {
    $jsonSchema: {
      bsonType: "object",
      required: ["_id", "name", "balance"],
      properties: {
        balance: { bsonType: "decimal", minimum: 0 }
      }
    }
  },
  validationAction: "error"
});
db.accounts.insertOne({ _id: 1, name: "Alice", balance: NumberDecimal("100.00") });
db.accounts.insertOne({ _id: 2, name: "Bad", balance: NumberDecimal("-1.00") });
// Document failed validation

// Simulation 2 fix: atomic predicate, one document
db.accounts.updateOne(
  { _id: 1, balance: { $gte: NumberDecimal("80") } },
  { $inc: { balance: NumberDecimal("-80") } }
);

// Letters — read consistency needs a snapshot transaction
db.letters.insertMany([
  { _id: 1, val: "a" }, { _id: 2, val: "b" }, { _id: 3, val: "b" },
  { _id: 4, val: "b" }, { _id: 5, val: "a" }, { _id: 6, val: "a" }
]);

const s = db.getMongo().startSession();
s.startTransaction({
  readConcern: { level: "snapshot" },
  writeConcern: { w: "majority" }
});
s.getDatabase("bank").letters.find().sort({ _id: 1 }).toArray();
// concurrent commits do not change this find
s.commitTransaction();

// Default db.letters.find() is NOT point-in-time — can stitch two commits (Sim 1)
```

No declarative FK. Prefer **embedding** related data in one document (single-doc atomicity). Cross-collection parent/child is application-level or a multi-doc transaction.

| Feature | PostgreSQL | InnoDB | MongoDB |
|---------|------------|--------|---------|
| PK / UNIQUE / NOT NULL | Yes | Yes | `_id` + unique index; `$jsonSchema` required |
| FK | Yes, deferrable | Yes (InnoDB only) | No |
| CHECK | Immediate, row-local | Yes (8.0.16+); `NOT ENFORCED` trap | `$jsonSchema` / `$expr` |
| Statement snapshot | RC default | RC | default `find` |
| Txn snapshot | RR = SI | RR first-read | `readConcern: snapshot` |
| Serializable | SSI `40001` | pessimistic locks | not offered |

## 5. Traps + 60-second interview version

| Trap | Reality |
|------|---------|
| "Every row is committed so the report is consistent" | Simulation 1. Read-C failed; data-C passed. |
| "CHECK means Alice cannot go negative under concurrency" | Simulation 2. Need atomic `WHERE balance >= n`. |
| "MongoDB `$lookup` is a foreign key" | It is a join at read time. It does not reject inserts. |
| "Replica lag is ACID C" | Lecture 16. The kiosk is stale **valid** data. |

### 60 seconds

> *"Consistency is overloaded. ACID C means valid state to valid state: the engine enforces PK, FK, CHECK; the app must preserve business invariants with correct transactions. That is different from read consistency: at Read Committed a multi-row SELECT can mix two commit points — Hussein's letter table can look like a mix that no serial execution produces, even though every letter is committed. Freeze the report with Repeatable Read, Snapshot, or Serializable. CHECK does not stop two concurrent withdrawals that each pass against a stale read — use an atomic UPDATE, FOR UPDATE, or Serializable. MongoDB uses schema validation and unique indexes; there is no FK; snapshot transactions give multi-document read consistency. Replica readConcern is a third word — don't mix it in."*

### Cheat sheet

1. Split C: data, read, replica.
2. Simulation 1 = incoherent **read**. Simulation 2 = broken **invariant**.
3. CHECK is per row. Cross-row needs isolation + correct SQL.
4. PG deferred ≠ CHECK. InnoDB `NOT ENFORCED` ≠ CHECK. MongoDB `$lookup` ≠ FK.
