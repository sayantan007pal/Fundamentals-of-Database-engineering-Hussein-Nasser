## 1. The one picture

Same transfer as lecture 8. Alice 100 → 0, Bob 50 → 150.

```text
scratch pad          receipt book              cash drawer
(buffer pool RAM)    (WAL / redo / journal)    (table / .wt files)

COMMIT stamps the receipt book.
Checkpoint later puts cash in the drawer.
```

Three volatile caches sit in front of the platters / NAND:

```text
DB buffer pool  --write()-->  OS page cache  --fsync-->  device cache  -->  media
   engine RAM                    kernel RAM              disk RAM         durable
```

`write()` returning means "the kernel copied the bytes." A power cut can still erase them. **`fsync` / `fdatasync`** is the stamp.

## 2. Simulation — five freeze-frames

Shared start:

```text
committed truth     Alice 100   Bob 50
T1 private view      Alice 100   Bob 50
WAL on media         (no this transfer)
data files           Alice 100   Bob 50
```

T1 runs:

```sql
BEGIN;
UPDATE accounts SET balance = 0   WHERE name = 'Alice';
UPDATE accounts SET balance = 150 WHERE name = 'Bob';
COMMIT;
```

### Frame 1 — changed only in the buffer pool

```text
committed truth     Alice 100   Bob 50     (T2 still sees this)
T1 private view     Alice   0   Bob 150
WAL on media         empty of this txn
OS page cache        empty of this WAL
data files           Alice 100   Bob 50
```

Crash here: **loser**. Transfer never happened. [9-Atomicity.md](9-Atomicity.md) Simulation 2a.

### Frame 2 — WAL written to the OS page cache, not fsynced

The engine called `write()` on the log file. The kernel has the COMMIT record in **RAM**. `fsync` has not finished. Some knobs ack the client **here**.

```text
WAL in OS cache      COMMIT XID 42   ← kernel thinks the write "succeeded"
WAL on media         not yet
data files           Alice 100   Bob 50
client               maybe already told "ok" if async commit
```

**Pause and predict:** Power cut (OS + RAM die). After restart, Alice = ?

**Reveal:** **100.** No durable COMMIT record on media. Loser. Database is **not corrupt** — you lost recent transactions.

This is PostgreSQL `synchronous_commit = off`, InnoDB `innodb_flush_log_at_trx_commit = 2` on **OS/power** crash, MongoDB `j: false` inside the ~100 ms journal window.

### Frame 3 — WAL fsynced, COMMIT acked, data files stale

This is the **modern default** (Process A).

```text
client               already received COMMIT success
WAL on media         COMMIT XID 42          ← durability lives here
data files           Alice 100   Bob 50      ← checkpoint has not run
```

**Pause and predict:** Crash 2 seconds later. After restart, Alice = ?

**Reveal:** **0**, Bob **150**. Recovery REDOs the WAL onto the stale data files. This is the sentence: **COMMIT means the log is durable, not that table files were rewritten.**

### Frame 4 — checkpoint flushed data pages

```text
WAL on media         COMMIT XID 42 (may now be recyclable)
data files           Alice 0   Bob 150
```

Crash here: still 0 and 150. Recovery has almost nothing to REDO. Checkpoints exist to **bound recovery time** and recycle log space — not to define COMMIT.

### Frame 5 — crash at 2 vs 3 vs 4 (cheat sheet)

| Crash at | COMMIT record on media? | After restart |
|----------|--------------------------|---------------|
| Frame 1 | No | Alice 100 |
| Frame 2 | No | Alice 100 (last commits **lost**) |
| Frame 3 | Yes | Alice 0, Bob 150 |
| Frame 4 | Yes | Alice 0, Bob 150 (short REDO) |

## 3. Why the engine does that

WAL **rule:** never write a dirty **data page** to disk until the log record describing it is already on stable storage.

Append-only **pattern:** the receipt book only adds pages (PostgreSQL WAL segments, InnoDB circular redo, MongoDB journal files). Sequential I/O + **group commit** (one fsync stamps many waiting transactions).

Checkpoint = **async snapshot** of data files. Redis RDB ≈ checkpoint; Redis AOF ≈ WAL pattern. PostgreSQL/InnoDB/MongoDB do **both**.

**STEAL / NO-FORCE** (lecture 9): data pages may leave RAM before commit; COMMIT does not wait for them. Only the log must reach Frame 3.

Torn pages: an 8 KB / 16 KB page is bigger than a 512-byte sector. Power cut mid-write → half old, half new. PostgreSQL **`full_page_writes`**: first change after a checkpoint logs the whole page. InnoDB **doublewrite buffer**: sequential copy, then in-place write.

## 4. Same idea in three engines

Which freeze-frame does **COMMIT wait for**?

| Engine knob | COMMIT waits until | Crash window |
|-------------|--------------------|--------------|
| PostgreSQL `synchronous_commit = on` (default) | Frame 3 WAL fsync | Safe |
| PostgreSQL `synchronous_commit = off` | Frame 2 (ack early) | May lose last ~few txns |
| InnoDB `innodb_flush_log_at_trx_commit = 1` (default) | Frame 3 redo fsync | Safe |
| InnoDB `= 2` | write() redo to OS cache; fsync ~1/s | Process crash: often OK. **OS/power:** ~1 s loss |
| InnoDB `= 0` | flush ~1/s from log buffer | Larger loss window |
| MongoDB `writeConcern: { w: 1, j: true }` | Frame 3 journal fsync on primary | Safe on that node |
| MongoDB `{ w: 1, j: false }` (default-ish) | Frame 2, journal sync ≤ ~100 ms | Hard shutdown may lose buffered writes |
| MongoDB `{ w: "majority", j: true }` | Frame 3 on a **majority of replicas** | Survives primary death |

Never `fsync = off` in PostgreSQL production. Unlogged tables skip WAL — empty after crash.

### PostgreSQL — type this

```sql
SHOW fsync;                 -- on
SHOW wal_sync_method;       -- fdatasync on Linux
SHOW synchronous_commit;  -- on  → Frame 3

BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE name = 'Alice' AND balance >= 100;
UPDATE accounts SET balance = balance + 100 WHERE name = 'Bob';
COMMIT;   -- XLogFlush + fdatasync, then "COMMIT" returns

-- Metrics: ack at Frame 2 (loss, not corruption)
BEGIN;
SET LOCAL synchronous_commit = off;
UPDATE metrics SET hits = hits + 1 WHERE id = 1;
COMMIT;

SELECT pg_current_wal_lsn();
-- CHECKPOINT;   -- admin only: force Frame 4

CREATE UNLOGGED TABLE session_cache (id INT PRIMARY KEY, data JSONB);
-- fast; truncated after crash
```

Files: `pg_wal/`, `pg_control`. Recovery: read last checkpoint LSN → REDO → missing COMMIT = abort.

### InnoDB — type this

```sql
SHOW VARIABLES WHERE Variable_name IN (
  'innodb_flush_log_at_trx_commit',  -- 1 = Frame 3
  'innodb_flush_method',             -- O_DIRECT typical
  'innodb_doublewrite',             -- ON (torn pages)
  'sync_binlog'                     -- 1 for replication durability; separate from redo
);

START TRANSACTION;
UPDATE accounts SET balance = balance - 100 WHERE name = 'Alice' AND balance >= 100;
UPDATE accounts SET balance = balance + 100 WHERE name = 'Bob';
COMMIT;

SET SESSION innodb_flush_log_at_trx_commit = 1;
SHOW STATUS LIKE 'Innodb_redo_log%';
```

`innodb_flush_log_at_trx_commit = 2`: mysqld crash often **no** loss (OS cache still has redo). Power loss: up to ~1 second gone. Not corrupt.

`sync_binlog` is for the **binary log** (replicas / PITR), not InnoDB redo. Name both.

### MongoDB — type this

```javascript
db.accounts.insertOne({ _id: "Alice", balance: NumberDecimal("100.00") });
db.accounts.insertOne({ _id: "Bob",   balance: NumberDecimal("50.00") });

// Frame 2 window (~100 ms journal buffer)
db.accounts.updateOne(
  { _id: "Alice" },
  { $inc: { balance: NumberDecimal("-100") } },
  { writeConcern: { w: 1, j: false } }
);

// Frame 3 on primary
db.accounts.updateOne(
  { _id: "Bob" },
  { $inc: { balance: NumberDecimal("100") } },
  { writeConcern: { w: 1, j: true } }
);

// Frame 3 on a majority of the replica set
db.accounts.updateOne(
  { _id: "Alice" },
  { $inc: { balance: NumberDecimal("-50") } },
  { writeConcern: { w: "majority", j: true } }
);

const session = db.getMongo().startSession();
session.startTransaction({ writeConcern: { w: "majority", j: true } });
try {
  const s = session.getDatabase("bank");
  s.accounts.updateOne({ _id: "Alice" }, { $inc: { balance: NumberDecimal("-100") } });
  s.accounts.updateOne({ _id: "Bob" },   { $inc: { balance: NumberDecimal("100") } });
  session.commitTransaction();  // one journal record
} catch (e) {
  session.abortTransaction();     // no journal record
}

db.adminCommand({ getParameter: 1, syncdelay: 1 });              // checkpoint ~60 s
db.adminCommand({ getParameter: 1, journalCommitInterval: 1 });  // ~100 ms
// db.adminCommand({ fsync: 1 });  // backup flush, NOT per-write durability
```

Interview trap: `db.adminCommand({ fsync: 1 })` is for **backups**. Per-write durability is **`j: true`**. Journaling cannot be turned off (6.1+). Checkpoint every 60 s writes `.wt` files (Frame 4).

| Concept | PostgreSQL | InnoDB | MongoDB |
|---------|------------|--------|---------|
| Log | WAL `pg_wal/` | redo `ib_logfile*` | journal `WiredTigerLog.*` |
| Data flush | checkpointer / bgwriter | checkpoint / eviction | checkpoint ~60 s |
| Torn-page fix | `full_page_writes` | doublewrite | WT reconciliation / checksums |
| COMMIT default | WAL fsync | redo fsync (`=1`) | journal interval ~100 ms unless `j` |

## 5. Traps + 60-second interview version

| Trap | Reality |
|------|---------|
| "`write()` hit disk" | `write()` hit the **OS page cache**. Frame 2. |
| "COMMIT updated the accounts file" | Frame 3 vs 4. |
| "Async commit corrupts the database" | It **loses** recent txns. Recovery is still consistent. |
| "MongoDB fsync command = durable insert" | `j: true` is per write. Admin `fsync` is backup. |
| "Majority write concern without journal" | On replica sets, majority usually implies journal (`writeConcernMajorityJournalDefault`). Still say `j` out loud for money. |

### 60 seconds

> *"Durability means once COMMIT returned, that transaction survives process crash, OS crash, and power loss. It does not mean every table page is on disk. Modern engines use a write-ahead log: they fsync the log, ack the client, and checkpoint data files later. write() is not enough — that is the OS page cache. The freeze-frame that matters is WAL on media. PostgreSQL synchronous_commit, InnoDB innodb_flush_log_at_trx_commit, and MongoDB writeConcern j choose whether COMMIT waits for that fsync or acks early and may lose the last few transactions. Crash recovery REDOs the log from the last checkpoint."*

### Cheat sheet

1. Five frames: RAM → OS cache → log on media → ack → data files.
2. Crash at 2 = loss. Crash at 3 = transfer stands.
3. Name the three knobs and which frame they wait for.
4. Group commit = one fsync, many waiters.
